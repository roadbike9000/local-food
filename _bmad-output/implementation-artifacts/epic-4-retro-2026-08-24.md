## What Went Well

- **Self-caught regressions never reached a test run, let alone review, in either story.** Story 4.1: an ATDD scaffold's "unauthenticated" test was actually running authenticated (fixed before implementation was called done). Story 4.2: a first draft of `ProductCard.tsx` added an extra wrapper `<div>`, which would have broken the `heading.locator("../..")` convention every existing storefront-cart test depends on — caught on re-reading the JSX before ever running Playwright, alongside an unrelated unbalanced-tag compile error in the same draft. Neither bug shipped; both were caught by re-reading own output, not by a reviewer.
- **A genuinely dangerous regression was introduced *while fixing a review finding*, in Story 4.1, and caught by regression discipline, not luck.** Patching the base64-content-validation finding first introduced a regex (`/^data:image\/(...)...;base64,[A-Za-z0-9+/]+={0,2}$/`) run against the full payload string. Under full-suite parallel load, this reproducibly threw `RangeError: Maximum call stack size exceeded` on the ~4.19MB oversized-payload test — an expected 400 turned into a real 500. Caught only because the full regression suite was re-run twice after applying patches, not just the touched file. Fixed by replacing the regex with a plain character loop (no recursion risk regardless of input length). This is the sharpest lesson of the epic: **a fix for one finding can introduce a worse bug than the one it closed, and only a full regression re-run (not just the new/changed tests) catches it.**
- **Story 4.2's Cloudinary-trust finding surfaced a subtle Next.js gotcha worth remembering: don't import a server-only, non-`NEXT_PUBLIC_`-prefixed env-derived constant into a `"use client"` component.** The natural fix for "re-validate `imageUrl` against this app's own Cloudinary cloud" would have been importing `CLOUDINARY_URL_PREFIX` straight into `ProductCard.tsx`. That constant is built from `process.env.CLOUDINARY_CLOUD_NAME`, which isn't public-prefixed — in the browser bundle it silently resolves to `undefined`, breaking the check for every visitor with no build error to catch it. The fix moved the check into the Server Component (`page.tsx`) instead, where `process.env` is genuinely available. Worth a durable rule: **before importing anything from a route's `schema.ts` into a client component, check whether it touches `process.env` at all.**
- **Epic 3's retro action items are now fully resolved — all 6, not just some.** Verified directly (not assumed): `npm run test:unit` is in `.github/workflows/ci.yml` (line 33); `POST /api/products`/`POST /api/pickup-slots` now call `assertVendorActive()`; `/api/admin/*` is now gated at the middleware layer (`src/middleware.ts`'s `isProtectedApiRoute`) and `E2E_ADMIN_EMAIL`/`E2E_ADMIN_CLERK_ID` are provisioned in CI secrets; the doc-accuracy and cross-order-atomicity lessons are codified as durable rules in `project-context.md`; the 3-epic roadmap was extended (Epic 4 and 5, from a scenario review with Jeff) rather than left as "complete." All of this happened in a session between Epic 3's retro and Epic 4's start — see Previous Retrospective Follow-Through below.
- **The doc-accuracy self-check (Epic 3 retro action item 4, now codified in `project-context.md`) was actually applied this time, not just scoped around.** Both stories explicitly re-investigated doc claims instead of assuming: Story 4.1 found the task's own line-number reference for `docs/data-models.md` pointed at the wrong field (`Vendor.imageUrl`, not `Product.imageUrl`) and said so in Completion Notes rather than silently "fixing" the wrong thing; Story 4.2 independently re-verified `docs/data-models.md`'s `Product.imageUrl` row was still accurate rather than trusting Story 4.1's prior finding. Neither review round flagged a doc-drift issue in either story — the first epic since this pattern started recurring (Epic 2 onward, per Epic 3's retro) where it didn't.
- **Epic 4 sidestepped the admin-credential gap entirely by construction, not by design choice.** Neither story touches `/api/admin/*` or `getCurrentAdmin()` at all — vendor upload and public storefront rendering are both outside that surface. 100% of both stories' new e2e coverage ran for real once Cloudinary was configured (see below), the same outcome Story 3.2's retro called "a genuine de-risking move" — except this time it wasn't a deliberate shape decision, just where the work happened to fall. Worth noting the distinction so it isn't miscredited as intentional risk management.

## What Slowed Us Down / Recurring Problems

**1. A new class of environment-configuration blocker showed up mid-story: third-party service credentials absent at session start.** Cloudinary wasn't configured when Story 4.1 began (`.env`'s `CLOUDINARY_*` values were 17/5/5-character placeholders) — genuinely required a HALT-and-ask rather than a workaround, since no amount of code discipline substitutes for a real account. Jeff configured it mid-session; the affected tests were un-skipped and re-verified. This is a different shape of blocker than the admin-credential gap (Epic 2–3's recurring issue) — that one is *known and chronic*; this one was *unknown until the first real upload attempt*. Worth a pre-flight check pattern: verify third-party service credentials exist (not just that env var names are documented in `.env.example`) before a story that depends on them begins, not after the first failed API call.

**2. `CLOUDINARY_*` is still not provisioned in CI, same shape of gap the admin credentials had for three epics.** `.github/workflows/ci.yml` has no `CLOUDINARY_*` secrets. Story 4.1's happy-path upload tests and Story 4.2's real-image test both self-skip gracefully when credentials are missing (the fix applied *during* Story 4.1's own review, learning from the admin-credential gap's history rather than repeating it blind) — so CI won't fail, but it also means 2 of the epic's ~15 e2e tests have never actually run in CI. This is a smaller-blast-radius version of Epic 2–3's admin-credential problem, caught and mitigated faster this time (within the same story, not three epics later) — but not actually closed.

**3. The story-file line-reference-to-code mismatch pattern (seen once in Epic 3 as a misattribution) showed up again, differently, in Story 4.1.** Task 5's bullet cited `docs/data-models.md:40` as the line needing an edit; by the time implementation started, that line was `Vendor.imageUrl`, not `Product.imageUrl` — a drift between when the story was written and when it was implemented, not a story-authoring mistake at the time. Caught by inspection rather than blind execution, but it's the second epic in a row where a story's own line-number citations didn't match the file's state by implementation time. Worth considering whether create-story should cite section headings instead of line numbers for anything not in the same commit as the story file itself.

## Key Insights

1. **A review finding's fix is new code, and new code needs the same regression discipline as the original implementation — sometimes more, since it's often written under time pressure to "just close the finding."** Story 4.1's regex-stack-overflow bug is the clearest evidence yet: a patch that looked obviously correct in isolation, passed typecheck, and even passed the *specific* test it was meant to fix, still broke a *different* test under load conditions that only a full-suite run reproduces. "Re-run the tests for the finding you fixed" is not the same discipline as "re-run everything," and this epic proved the gap between them is not hypothetical.
2. **Naming a lesson in a retrospective and codifying it as a durable rule are different levels of commitment, and the difference showed up as different outcomes this epic.** Epic 3's retro *named* the doc-accuracy and atomicity lessons; between epics, they got promoted into `project-context.md` as standing rules. This epic, both lessons held (doc-accuracy: zero drift findings in review; atomicity: not tested since no concurrent-invariant code was touched, but no regression either). Compare to Epic 3's own retro, which noted the *named-but-not-yet-codified* version of these same lessons only partially transferred. This is one epic's worth of evidence, not proof, but it's consistent with the theory.
3. **Sidestepping a known blocker "by construction" (the work just doesn't touch it) reads identically to "by design" in outcome, but the two are not the same kind of win.** Story 3.2 deliberately shaped itself to avoid the admin-credential gate. Epic 4 avoided it because neither story happened to need `/api/admin/*`. Both get 100% real e2e coverage; only one is a repeatable technique. Worth being precise about which one happened, so future retros don't credit "design" where it was actually "topic."
