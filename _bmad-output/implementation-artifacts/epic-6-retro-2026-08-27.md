## What Went Well

- **The adversarial review caught a real bug that 11 passing unit tests — including 4 explicitly labeled "DST boundary" cases — did not.** `zonedWallTimeToUtc()`'s single-pass offset lookup was wrong for a several-hour window around every DST transition in the schema's own default zone. Every test written during ATDD sampled `09:00`, a time that happens to sit outside the broken window in both directions — the story's own Dev Notes explicitly warned this exact failure mode was possible, and it happened anyway, past a "cross-checked against Python's `zoneinfo`" verification step that felt rigorous at the time. All three review layers (Blind Hunter, Edge Case Hunter, Acceptance Auditor) independently reproduced the identical defect **by execution**, not by inspection — strong signal this was a true positive, not review noise.
- **The bug was verified, not trusted, at every step of the response — in both directions.** Before fixing anything, the bug itself was independently reproduced with a round-trip check before accepting the reviewers' claim. One reviewer's specific claim ("empty input throws a `RangeError`") was checked directly in Node before being treated as fact — it turned out to be wrong in an interesting way (the real behavior, silently producing a year-2000 date, was worse than the claimed one). Every new test value added during the fix was cross-checked against Python's `zoneinfo` independently, not derived from the fixed implementation itself. This is the same "verify, don't blindly implement" discipline this project's `receiving-code-review` conventions call for, applied all the way through.
- **ATDD's deliberate scoping decision — test only the DB-independent conversion module, defer DB-dependent scenarios to `dev-story` — was the right call, confirmed in hindsight.** The one piece that got genuine red-phase coverage during ATDD is also the piece that turned out to have the real bug. Scoping ATDD tightly to what could be tested in true isolation, rather than force-fitting a migration into the wrong phase to make broader tests possible, meant the highest-risk code got the most rigorous phase-appropriate scrutiny.
- **`create-story`'s reference algorithm, written before any code existed, correctly anticipated the shape of the risk** ("DST transitions are easy to get subtly wrong... treat Task 2's Vitest coverage as this story's actual acceptance bar") — the warning was accurate; what it couldn't anticipate was that the same author's later test-case selection would still miss the specific window that warning was about.
- **Grep-every-call-site discipline (an explicit Task 4 instruction) found 2 real, unplanned `cart/page.tsx` call sites** for `formatPickupWindow()` that neither the epic nor the story anticipated — fixed in scope with a corresponding API-contract addition, not left as a silent gap.

## What Slowed Us Down / Recurring Problems

**1. The same author wrote the algorithm, the tests, and the implementation across three different pipeline phases, and the same blind spot survived all three.** `create-story` specified the reference algorithm and named DST as the risk. `bmad-testarch-atdd` wrote the test cases against that same mental model. `dev-story` implemented against those tests. All three phases individually did real, verifiable work (the algorithm reference was directionally correct; the tests' expected *values* were genuinely correct; the implementation genuinely satisfied every test written) — but none of the three phases, on their own, ever asked "have I chosen a test time that's actually *inside* the risky window, or just *on* the risky day?" A checklist requirement ("at least one real DST-transition-boundary case") was satisfied in letter by every phase's own logic without ever being satisfied in substance, because nothing in the pipeline forced an adversarial check on the test *selection* itself until an independent reviewer came in cold. This is a sharper version of a lesson this project has named before (Epic 4's "a review finding's fix is new code, needs the same regression discipline") — here it's not a fix under time pressure, it's the *original* work, carried through three phases by the same reasoning, un-caught until genuinely independent review arrived.
**2. "Cross-checked against an independent oracle" validated the wrong thing.** The ATDD pass's Debug Log (and this story's own) proudly noted every DST test's expected value was independently verified against Python's `zoneinfo` — true, and a real, worthwhile check. But it verifies that *given a chosen input, the expected output is correct* — it says nothing about whether the *chosen input* actually exercises the code's riskiest path. Both are needed; only one was done until the review round.

## Key Insights

1. **"At least one DST-boundary test case" is an underspecified acceptance bar — the meaningful requirement is a test case *inside the actual broken window*, and the only way to know where that window is, is to have already found (or specifically hunted for) the bug.** For a future story touching timezone/offset math, the more useful instruction is not "add a DST test" but "sweep a range of times across the transition day and confirm every one round-trips" — a property-style check that can't be satisfied by accidentally picking a safe time.
2. **Independent review earns its cost precisely when the same reasoning has been applied multiple times by the same source.** This epic is the clearest evidence yet in this project that a multi-phase AI-driven pipeline (spec → tests → implementation) is not automatically self-correcting just because each phase does real verification work — the verification each phase performs is scoped to what that phase controls, not to blind spots inherited from an earlier phase. Jeff's standing preference for Opus specifically on code review, and for review to be genuinely adversarial rather than confirmatory, is well-supported by what happened here.
3. **A "genuine external proof, not a tautology" framing (used throughout this story's own tests and Completion Notes) is a real and valuable discipline — worth keeping — but it's not sufficient on its own.** The DST tests *were* independently cross-checked against an external oracle and still missed the bug, because the discipline was applied to value-correctness, not case-selection. Both matter; naming only one risks false confidence.
