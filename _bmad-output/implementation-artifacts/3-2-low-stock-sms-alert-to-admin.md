# Story 3.2: Low-stock SMS alert to admin

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an admin,
I want a text when a product's stock crosses its low-stock threshold,
so that I can act before it sells out.

## Acceptance Criteria

1. `Admin` gains a `phone` field (mirrors `Vendor.phone`'s exact shape: `String?`, nullable) — required to actually deliver this story, missing from the original schema (Story 2.1 deliberately excluded it).
2. When a product's Stock Quantity crosses at or below its Low-Stock Threshold as part of a Story 1.4 decrement, the caller sends an SMS to the admin's phone via the existing `sendSms` module.
3. `lowStockAlerted` is set true only after the send succeeds — never before, mirroring the existing `smsNotified` pattern.
4. A failed send leaves `lowStockAlerted` false — it is never marked delivered.
5. Further sales while stock stays below threshold do not trigger repeat alerts, until stock is restocked above threshold and crosses again.
6. A post-payment shortfall result from Story 1.4's `decrementStock()` (money captured, stock insufficient under a race) also triggers this same SMS mechanism to the admin's phone — closing the loop Epic 1 intentionally left open since Admin didn't exist yet at that point.

*(FR10, FR8's shortfall consequence, AD-3, NFR3.)*

## Dev Notes

**This story changes two of the most heavily-reviewed function signatures in the codebase (`decrementStock()`, `setStock()`) — both from Story 1.4/1.2, both survived 3-4 review rounds each in Epic 1.** Read `src/lib/inventory.ts` in full before touching either. The signature changes are deliberate, spec-driven (architecture AD-3 explicitly states "`decrementStock()` returns whether the threshold was newly crossed"), not incidental — but every existing call site (webhook route, `products/[id]/route.ts`, and ~12 direct test calls across `tests/inventory.spec.ts`) must be updated in the same pass. Do not leave any call site on the old signature; `tsc` will catch missed ones but confirm by grep too (`grep -rn "decrementStock\|setStock(" src/ tests/`).

**Decision made during this story's planning (not left to the dev agent): `Admin.phone` is `String?` (nullable), not required.** Epics.md's phrase "required to actually deliver this story" describes a *functional* precondition (no phone means no SMS can be sent for that admin), not a schema-level `NOT NULL` constraint — it mirrors `Vendor.phone`'s exact existing shape (also `String?`), and a schema-required phone with no admin-management UI to collect it would make every `Admin` row created via the existing seed/manual-DB-write flow (Story 2.1's pattern) immediately invalid. A zero-admins-with-a-phone state must degrade gracefully (no SMS attempted, no crash, no error) — this is the expected, normal state of most dev/staging environments, mirroring Twilio's own existing "no creds configured → no-op and log" philosophy already established in this codebase.

**Decision made during this story's planning: alerts fan out to every `Admin` row with a phone set, not "the" admin.** Nothing in this codebase's schema or prior stories enforces exactly one `Admin` row — Story 2.1 seeded one for test purposes, but a real deployment could reasonably have more than one operator. `getAdminPhoneNumbers()` returning an array and looping over it costs nothing extra in complexity over hardcoding a single lookup, and avoids silently dropping alerts for a second/third admin the moment one gets added.

**Decision made during this story's planning: the shortfall SMS (AC #6) uses a distinct message and is never gated by `lowStockAlerted`.** A shortfall means a customer's payment was already captured and the order can't be fully fulfilled — a fundamentally different, more urgent event than "stock is getting low," and epics.md's own phrasing ("also triggers this same SMS *mechanism*," not "the same message") supports reusing the *infrastructure* (admin-phone lookup, `sendSms()`) without reusing the *text* or the *dedupe flag*. Deduping a shortfall alert against `lowStockAlerted` would be actively wrong: a shortfall can recur on genuinely different orders even while the flag stays `true` from an earlier routine crossing, and each shortfall represents real money already charged for goods that couldn't ship — worth surfacing every time, not once.

**SMS sending must happen after the transaction commits, never inside it.** `decrementStock()`'s job (Task 2) is limited to *reporting* a crossing from inside the transaction (a pure DB read, safe under the held row lock) — the actual `sendSms()` network call and the `lowStockAlerted`/nothing-for-shortfalls write both happen in Task 5, strictly after `prisma.$transaction(...)` resolves. This mirrors the existing `smsNotified` pattern exactly (`order.smsNotified` is also set only after the transaction, via a separate `sendSms()` call) and avoids holding a DB row lock across a slow/failing external network call.

**No new atomic-claim mechanism is needed for `lowStockAlerted`.** Unlike `stockDecremented` (which needed an atomic claim to survive concurrent webhook deliveries of the *same* event), `crossedLowStock` is computed *inside* a transaction that's already gated by the existing outer `stockDecremented` atomic claim — only one concurrent delivery of a given event ever reaches the per-item `decrementStock()` loop at all. A plain conditional `prisma.product.update()` after a successful send is sufficient, matching `smsNotified`'s existing plain-write shape.

**`sendSms()`'s existing contract is unchanged and must not be modified.** It already returns `boolean` (success) and never throws, logging failures internally (`src/lib/sms/index.ts`) — this story is a pure consumer of that contract via two new message-string builders, not a change to the SMS layer itself.

**`project-context.md`/`CLAUDE.md` reference `src/lib/twilio.ts` for SMS — this is stale.** The actual current module is `src/lib/sms/index.ts` (a provider-abstraction layer, `providers/{twilioProvider,mockProvider}.ts`), already the *only* import path the Stripe webhook uses (`import { sendSms, orderConfirmedMessage } from "@/lib/sms"`). Use `@/lib/sms`, not `@/lib/twilio.ts` (which may not even exist anymore — verify before assuming either way). This staleness is pre-existing, not introduced by this story, and out of this story's scope to fix in `project-context.md` itself (that file's own maintenance note says "Update when technology stack changes" — flag it in Dev Agent Record if confirmed stale, don't silently patch a doc file outside this story's own doc-sync task).

### Review Findings — Round 1 (2026-08-22, Opus, reviewing commit range `de02699..9ce8004`)

_Three-layer adversarial pass (Blind Hunter, Edge Case Hunter, Acceptance Auditor), all Opus. All three independently converged on the same top bug (a shortfall's compensation rollback still fired a false low-stock alert and permanently poisoned `lowStockAlerted`); two of three also independently found the stale-threshold bug in the PATCH route and the concurrent-order race on the alert flag. This is the first story this session where all three layers agreed on the same top finding before any triage — high confidence signal. The orchestrator independently reproduced the top finding by temporarily reverting the fix and re-running the new regression test, confirming it fails exactly as predicted, then restored the fix._

**Resolved (Patch):**

- [x] **Critical: a shortfall's compensation rollback still fired a low-stock alert for the rolled-back product, permanently disarming its real future alerts.** `crossedLowStockProductIds` was collected from `applied` items inside the transaction, but on any shortfall in the same order, the compensation loop increments *every* `applied` decrement back — including ones that had crossed their threshold. The list was still returned unfiltered, so the post-commit block sent a self-contradicting "down to N units" text for a product sitting back at its original stock, then set `lowStockAlerted: true` on it — silencing all future genuine crossings until an explicit restock via `setStock()`. Confirmed independently by all three review layers, then verified directly: reverted the fix, re-ran the new regression test, watched it fail with the exact predicted symptom (`lowStockAlerted: true` on an unchanged-stock product), restored the fix, watched it pass. **Fix: the shortfall-return branch now returns `crossedLowStockProductIds: []` unconditionally** — nothing in that list ever survives a shortfall in the same order, matching the early-return branch's existing shape. **New regression test added** (`tests/webhooks.spec.ts`, multi-item order with one crossing line + one shortfalling line) proving the fix and guarding against a re-regression.
- [x] **High: the PATCH route passed the pre-write threshold to `setStock()`'s restock-reset check.** `product.lowStockThreshold` was read *before* `setLowStockThreshold()` wrote the new value, then handed to `setStock()` as `currentThreshold` — comparing the new stock value against a threshold the row no longer had. A PATCH that changes both fields (the form always posts both) could reset `lowStockAlerted` against the *old* threshold or fail to reset it against the *new* one, in either direction. **Fix: pass the just-parsed `lowStockThreshold`, not `product.lowStockThreshold`.**
- [x] **High: two different orders concurrently crossing the same product's threshold could both send an alert.** The story's own reasoning ("no atomic claim needed... only one concurrent delivery of a given event ever reaches this code path") is correct about *one order's* event but doesn't cover *two different orders* racing to decrement the same product — the normal shape of two customers competing for the last few units, not an exotic case. **Fix: `lowStockAlerted` is now claimed atomically via `updateMany({ where: { id, lowStockAlerted: false } })` *before* sending, not after** — a second concurrent crosser sees `claim.count === 0` and skips. If the send then fails, the claim is explicitly reverted back to `false`, so AC #4 ("never left true without an actual successful send") still holds and a later crossing can retry.
- [x] **Medium: `setStock()`'s restock-reset check re-derived the low-stock comparison instead of reusing `isLowStock()`**, drifting from it at a negative threshold (unreachable today, but the canonical-check principle this codebase already applies elsewhere — AD-2 — was violated). **Fix: `!isLowStock({ stockQuantity: newValue, lowStockThreshold: currentThreshold })`, matching `decrementStock()`'s own reuse of the same function.**
- [x] **Medium: the AC #4 "failed send" test was vacuous — it couldn't distinguish "attempted and failed" from "never ran at all."** The mock provider's `MAGIC_FAILURE_NUMBER` branch returned early without recording anything, so the test's only assertion (`lowStockAlerted === false`) would pass identically if the entire alert block were deleted. **Fix: the mock provider now records failed attempts too** (`SentMessage` gained a `success: boolean` field), and the test asserts a message was actually recorded with `success: false` for this product — a real positive control. Also gave this test's fixture an explicit unique product name, matching the other three (it was the one exception the "each of this story's 4 fixtures" claim didn't actually cover — now it does).
- [x] **Medium: admin SMS fan-out sat on the webhook's critical path ahead of the customer's own confirmation SMS.** A slow or hanging admin-alert loop (multiple products × multiple admin phones, sequential sends) could delay or, on a timeout, entirely skip the customer's "your order is confirmed" text. **Fix: moved the customer-confirmation block to run first**, immediately after the PAID transition and independent of `stockDecremented` (unchanged retry-recovery semantics) — admin bookkeeping can no longer block or delay it.
- [x] **Low-medium: `shortfall.available ?? 0` reported a deleted product as "0 available"**, losing the deliberate `null` = "product no longer exists" distinction `ShortfallDetail` already carries. **Fix: the shortfall message now says "unknown (product deleted)"** when `available` is `null`, never a misleading literal `0`.
- [x] **Low: two `OrderItem` lines for the same product in one shortfalling order sent two identical shortfall texts.** **Fix: shortfalls are now aggregated by `productId` (summing `requested`) before sending**, so one product generates exactly one text per order regardless of how many lines it appears on.
- [x] **Low: an empty-string `Admin.phone` counted as a successful delivery target**, since `{ phone: { not: null } }` doesn't exclude `""`. **Fix: `getAdminPhoneNumbers()` now trims and filters out blank values**, and deduplicates the result (nothing prevents two `Admin` rows sharing one phone, which would otherwise double-send every alert).
- [x] **Low: `getAdminPhoneNumbers()` was queried twice per webhook call** when both a shortfall and a crossing fired in the same order. Left as two separate calls (one per block) rather than hoisted to a single shared call above both — the blocks are independently gated (`if (result.shortfalls.length > 0)` / `if (result.crossedLowStockProductIds.length > 0)`) and hoisting would mean fetching phones even when neither block needs them; the duplicate-query cost is one extra indexed read on the rare order that hits both paths, not worth the extra shared-state plumbing.
- [x] **Doc accuracy: `docs/api-contracts.md`'s step 6b claimed the crossing and shortfall cases "both can fire from the same webhook call" without qualification** — true before the fix above, no longer accurate after it (a shortfall on any line empties the crossing list for the whole order). **Fix: renumbered and rewrote steps 6-7b to reflect the actual execution order** (customer SMS now documented before the decrement/alert block, matching the code) **and the corrected crossing-suppression behavior.**
- [x] **Doc accuracy: the ATDD checklist and a Dev Notes comment both had incorrect test-count arithmetic** (an internally-inconsistent "33 pre-existing + 11 new = 44" split, and an approximated "~29" pre-existing webhook tests where the real count was 19). **Fixed both to the correct figures.**

**Dismissed, with reasoning:**

- *`decrementStock()`'s extra `findUnique` per line item, inside the payment-critical lock window.* — A deliberate, explicitly-justified tradeoff made during this story's own planning (Dev Notes: "safe and consistent because the row lock... is still held," chosen over a riskier design). Multi-item orders in this app are typically small; the existing 15s `lock_timeout` already bounds the worst case. Revisit only if this measurably matters in practice, not preemptively.
- *The shortfall SMS has no delivery guarantee or retry path.* — Matches the exact same terminal-shortfall, `Sentry.captureException` + `console.error`, "a human resolves it" pattern this identical code block already used for shortfall reporting before this story existed. The SMS is additional best-effort visibility layered on that already-accepted mechanism, not the sole channel; building a guaranteed-delivery outbox is materially larger scope than this story's stated goal.
- *The `globalThis` cache guard (`NODE_ENV !== "production"`) reintroduces the cross-route module-isolation bug for a production deployment running the mock SMS provider.* — Matches `src/lib/prisma.ts`'s identical existing guard exactly, and the only consumer of the shared array (`/api/debug/sms`) is independently gated to 404 in production regardless — there's no path for the reintroduced bug to actually surface.
- *`setStock()`'s new signature is four consecutive positional `number`-typed parameters — a future misordered call would typecheck silently.* — Real risk in the abstract, but every existing call site is already migrated and correct (verified by `grep`); redesigning to an options object now would be new scope on a signature that just shipped, not a fix to anything currently broken. Worth considering if this function's parameter list grows again.
- *A threshold-only edit (no stock change) doesn't reset `lowStockAlerted`, even when the new threshold moves below current stock.* — Explicitly out of scope per this story's own Task 3 ("out of this AC's literal scope... a different concern this story doesn't address"), not an oversight.
- *A product with a placeholder (`0`) threshold selling out produces "down to 0 units (threshold: 0)."* — Not misleading: a threshold of `0` legitimately means "alert only at literal zero," and the message states exactly that truthfully. Distinguishing "vendor never reviewed this threshold" from "vendor deliberately chose 0" in the alert text would be a real enhancement but isn't required by any AC.
- *An admin test fixture could leak past its `finally` block on a hard worker crash, permanently polluting a later run of the AC #4 test.* — Matches this codebase's universal try/finally cleanup convention, used by every fixture in every test file; not a new risk this story introduces, and no story to date has built crash-safe fixture teardown.
- *Phone sends within a product's admin loop are sequential, not `Promise.all`-parallelized.* — Correctness is unaffected either way; sequential is simpler and matches this file's other loops (the shortfall compensation loop, the existing decrement loop). Not worth the added complexity for a latency win with no current evidence it matters.
