# Story 3.2: Low-stock SMS alert to admin

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an admin,
I want a text when a product's stock crosses its low-stock threshold,
so that I can act before it sells out.

## Acceptance Criteria

1. `Admin` gains a `phone` field (mirrors `Vendor.phone`'s exact shape: `String?`, nullable) — required to actually deliver this story, missing from the original schema (Story 2.1 deliberately excluded it).
2. When a product's Stock Quantity crosses at or below its Low-Stock Threshold as part of a Story 1.4 decrement, the caller sends an SMS to the admin's phone via the existing `sendSms` module.
3. `lowStockAlerted` is set true only after the send succeeds — never before, mirroring the existing `smsNotified` pattern.
4. A failed send leaves `lowStockAlerted` false — it is never marked delivered.
5. Further sales while stock stays below threshold do not trigger repeat alerts, until stock is restocked above threshold and crosses again.
6. A post-payment shortfall result from Story 1.4's `decrementStock()` (money captured, stock insufficient under a race) also triggers this same SMS mechanism to the admin's phone — closing the loop Epic 1 intentionally left open since Admin didn't exist yet at that point.

*(FR10, FR8's shortfall consequence, AD-3, NFR3.)*

## Dev Notes

**This story changes two of the most heavily-reviewed function signatures in the codebase (`decrementStock()`, `setStock()`) — both from Story 1.4/1.2, both survived 3-4 review rounds each in Epic 1.** Read `src/lib/inventory.ts` in full before touching either. The signature changes are deliberate, spec-driven (architecture AD-3 explicitly states "`decrementStock()` returns whether the threshold was newly crossed"), not incidental — but every existing call site (webhook route, `products/[id]/route.ts`, and ~12 direct test calls across `tests/inventory.spec.ts`) must be updated in the same pass. Do not leave any call site on the old signature; `tsc` will catch missed ones but confirm by grep too (`grep -rn "decrementStock\|setStock(" src/ tests/`).

**Decision made during this story's planning (not left to the dev agent): `Admin.phone` is `String?` (nullable), not required.** Epics.md's phrase "required to actually deliver this story" describes a *functional* precondition (no phone means no SMS can be sent for that admin), not a schema-level `NOT NULL` constraint — it mirrors `Vendor.phone`'s exact existing shape (also `String?`), and a schema-required phone with no admin-management UI to collect it would make every `Admin` row created via the existing seed/manual-DB-write flow (Story 2.1's pattern) immediately invalid. A zero-admins-with-a-phone state must degrade gracefully (no SMS attempted, no crash, no error) — this is the expected, normal state of most dev/staging environments, mirroring Twilio's own existing "no creds configured → no-op and log" philosophy already established in this codebase.

**Decision made during this story's planning: alerts fan out to every `Admin` row with a phone set, not "the" admin.** Nothing in this codebase's schema or prior stories enforces exactly one `Admin` row — Story 2.1 seeded one for test purposes, but a real deployment could reasonably have more than one operator. `getAdminPhoneNumbers()` returning an array and looping over it costs nothing extra in complexity over hardcoding a single lookup, and avoids silently dropping alerts for a second/third admin the moment one gets added.

**Decision made during this story's planning: the shortfall SMS (AC #6) uses a distinct message and is never gated by `lowStockAlerted`.** A shortfall means a customer's payment was already captured and the order can't be fully fulfilled — a fundamentally different, more urgent event than "stock is getting low," and epics.md's own phrasing ("also triggers this same SMS *mechanism*," not "the same message") supports reusing the *infrastructure* (admin-phone lookup, `sendSms()`) without reusing the *text* or the *dedupe flag*. Deduping a shortfall alert against `lowStockAlerted` would be actively wrong: a shortfall can recur on genuinely different orders even while the flag stays `true` from an earlier routine crossing, and each shortfall represents real money already charged for goods that couldn't ship — worth surfacing every time, not once.

**SMS sending must happen after the transaction commits, never inside it.** `decrementStock()`'s job (Task 2) is limited to *reporting* a crossing from inside the transaction (a pure DB read, safe under the held row lock) — the actual `sendSms()` network call and the `lowStockAlerted`/nothing-for-shortfalls write both happen in Task 5, strictly after `prisma.$transaction(...)` resolves. This mirrors the existing `smsNotified` pattern exactly (`order.smsNotified` is also set only after the transaction, via a separate `sendSms()` call) and avoids holding a DB row lock across a slow/failing external network call.

**No new atomic-claim mechanism is needed for `lowStockAlerted`.** Unlike `stockDecremented` (which needed an atomic claim to survive concurrent webhook deliveries of the *same* event), `crossedLowStock` is computed *inside* a transaction that's already gated by the existing outer `stockDecremented` atomic claim — only one concurrent delivery of a given event ever reaches the per-item `decrementStock()` loop at all. A plain conditional `prisma.product.update()` after a successful send is sufficient, matching `smsNotified`'s existing plain-write shape.

**`sendSms()`'s existing contract is unchanged and must not be modified.** It already returns `boolean` (success) and never throws, logging failures internally (`src/lib/sms/index.ts`) — this story is a pure consumer of that contract via two new message-string builders, not a change to the SMS layer itself.

**`project-context.md`/`CLAUDE.md` reference `src/lib/twilio.ts` for SMS — this is stale.** The actual current module is `src/lib/sms/index.ts` (a provider-abstraction layer, `providers/{twilioProvider,mockProvider}.ts`), already the *only* import path the Stripe webhook uses (`import { sendSms, orderConfirmedMessage } from "@/lib/sms"`). Use `@/lib/sms`, not `@/lib/twilio.ts` (which may not even exist anymore — verify before assuming either way). This staleness is pre-existing, not introduced by this story, and out of this story's scope to fix in `project-context.md` itself (that file's own maintenance note says "Update when technology stack changes" — flag it in Dev Agent Record if confirmed stale, don't silently patch a doc file outside this story's own doc-sync task).
