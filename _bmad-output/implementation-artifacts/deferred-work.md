- source_spec: `_bmad-output/implementation-artifacts/1-2-stock-quantity-captured-at-creation-backfilled-for-existing-products.md`
  summary: A vendor who deliberately wants a placeholder-valued field (Low-Stock Threshold = 0, or Stock Quantity = 0 for a product that was `isAvailable: false` at migration time) cannot mark that as deliberate **in a single save** — both `thresholdIsPlaceholder`/`stockIsPlaceholder` only clear on a genuine value change, and resubmitting the same value leaves the flag `true`. There is a two-step workaround (change the value, save, change it back, save again — each save is a "genuine change" relative to the value just before it), but nothing in the UI surfaces that, so in practice a vendor who wants exactly the placeholder value has no discoverable way to confirm it. Story 1.6 needs to account for this before it builds the low-stock-flagging (and any stock-flagging) logic on top of these flags.
  evidence: Review round 3, finding M5, corrected and extended per round 4. Original M5 wording claimed the threshold case "can never" be marked deliberate and that `stockIsPlaceholder` "self-heals since 100 is an unusual value to land on twice" — both points needed correction: the two-step workaround exists (round 4), and the self-healing claim is false for any product backfilled to `stockQuantity = 0` (products that were `isAvailable: false` when the original migration ran, per `20260818151647_.../migration.sql:14`'s `CASE WHEN "isAvailable" THEN 100 ELSE 0 END`) — those hit the identical same-value trap as the threshold. Not currently exercised (all 5 dev-seed products are `isAvailable: true` / stock 100), but a live code path on any other environment with a mix of available/unavailable products at migration time. Fixing it cleanly needs the client to send a dirty-field signal (only include a field in the PATCH body when the vendor actually touched that specific input) rather than always resubmitting both — new API-surface scope beyond a review-response patch. Accepted as-is for Story 1.2.
