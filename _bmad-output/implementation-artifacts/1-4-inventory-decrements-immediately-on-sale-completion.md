# Story 1.4: Inventory decrements immediately on sale completion

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the platform,
I want stock to drop the moment a sale is confirmed,
so that inventory never says "in stock" when it isn't.

## Acceptance Criteria

1. Given a Stripe webhook confirms payment (`checkout.session.completed`) for an order, when that order first transitions from `PENDING` to `PAID`, then each of its `OrderItem` lines' `Product.stockQuantity` decrements by that line's `quantity` through a new `decrementStock()` function — a conditional update that never takes `stockQuantity` negative.
2. A multi-item order's decrements all happen inside one Prisma transaction — every line's decrement succeeds, or none of them are applied (full rollback on any single line's shortfall).
3. Two concurrent decrement attempts against the same product's last unit (e.g. two different customers' orders both containing that product, webhooks racing) resolve deterministically to exactly one success and one rejection — never negative stock, never a double-sale of the same unit.
4. Stock is never decremented at checkout-session creation (`POST /api/checkout`) — only in the webhook, only after Stripe confirms payment. (`/api/checkout` already only *reads* `stockQuantity` for its Story 1.3 sufficiency check — verify this story doesn't add a write there.)
5. When `decrementStock()` reports insufficient stock for a line — a post-payment race: Stripe has already captured the customer's money, but stock ran out before this webhook processed it — the webhook does not silently over-decrement or auto-refund, and does not fail/reject the webhook itself (payment already happened; there's nothing to "reject" at this point — `order.status` still becomes `PAID`). The shortfall must not be silently swallowed: surface it (e.g. `Sentry.captureMessage`/`captureException`, consistent with this codebase's existing error-visibility pattern), but do **not** send any customer/admin notification — that's Story 3.2's job once an Admin identity exists (Epic 2).
6. **Derived requirement, not literal epics.md text but required for AC #1/#3 to hold correctly under Stripe's webhook retry semantics:** a replayed webhook for an order whose stock was already decremented on a prior call (Stripe retries on timeout/5xx — see `tests/webhooks.spec.ts`'s existing `smsNotified` replay test) must **not** decrement stock a second time. `project-context.md` already flags this exact gap: *"Webhook is not idempotency-guarded beyond `smsNotified` — don't assume replay-safety when extending it."* Without a guard, `decrementStock()`'s own sufficiency check (`stockQuantity >= quantity`) does **not** protect against this — a replay with enough remaining stock would happily decrement a second time, silently overselling the vendor's real inventory downward.

*(FR8, AD-3, NFR1 — "Stock Quantity changes (decrement, threshold check) must be consistent under concurrent orders — no overselling the last unit.")*

## Dev Notes

**This is the first story to introduce a real second writer racing against `setStock()`'s optimistic lock — and the first `prisma.$transaction()` usage anywhere in this codebase.** `grep -rn "\$transaction" src/` currently returns nothing. Both are genuinely new territory here, not just "another `src/lib/inventory.ts` export" — budget real verification time for the transaction wrapping actually rolling back correctly (Task 6's shortfall/race tests are what prove it, not just typechecking).

**Idempotency design note (AC #6):** this story deliberately does **not** add a new `Order.stockDecremented`-style boolean column. Instead it reuses the existing `status` field as the one-shot guard, via a conditional `updateMany({ where: { status: { not: "PAID" } }, data: { status: "PAID" } })` + `count === 1` check (Task 2). This ties "decrement stock exactly once" to the same domain event ("this order just became PAID for the first time") rather than inventing a second, parallel flag that could drift out of sync with it — and avoids a migration entirely. One consequence worth knowing: once `status` flips to `PAID` on the first webhook call, a *later* Stripe retry will never re-attempt a shortfalled decrement even if stock was replenished in the meantime — the shortfall is terminal for that order, to be resolved by a human (Story 3.2's eventual SMS-driven admin follow-up), not by hoping a retry succeeds differently. This matches AD-3's own framing ("not auto-resolved... flagged for manual admin review").

**`decrementStock()`'s transaction-client-only signature is a convention, not a fully type-enforced guardrail.** Prisma's `Prisma.TransactionClient` type is structurally a *subset* of the full `PrismaClient` interface (it omits `$transaction`/`$connect`/etc.) — which means TypeScript's structural typing will still happily accept the bare `prisma` singleton wherever a `Prisma.TransactionClient` parameter is expected. Nothing at the type level stops a future caller from passing `prisma` directly and silently running `decrementStock()` outside a transaction. The only real defense is discipline (always call it from inside the webhook's `$transaction` callback, never elsewhere) plus this story's own shortfall/rollback tests, which would start failing if that discipline slipped. Flag this for the code reviewer to check by inspection, not just by re-running tests.

**Don't build Story 3.2's plumbing early.** Architecture AD-3's prose describes `decrementStock()` eventually "returning whether the threshold was newly crossed" so a caller can fire a low-stock SMS. That capability, `Product.lowStockAlerted`, and `Admin.phone` all belong to Story 3.2 (Epic 3, which needs Epic 2's Admin identity to exist first) — building them now is scope creep with nothing to consume them yet. This mirrors the exact discipline the last two stories already established: Story 1.2's Dev Notes said *"`decrementStock()` is not part of this story... leave `inventory.ts` with just what this story needs"*; Story 1.3's said *"Don't wire up decrementing stock in this story... resist the urge to 'finish the job'."* This story is where `decrementStock()` finally gets built — build exactly what AC #1-#6 need, nothing that anticipates Story 3.2's needs.

**A correction to be aware of, not a contradiction to chase down:** the brief for this story's context-gathering pointed at `tests/inventory.spec.ts` as having "the existing pattern testing `setStock`'s conditional-update race behavior." Having read that file in full, it does **not** — its 7 current tests (added across Story 1.2's review rounds) cover the conditional-update success/rejection cases and the placeholder-flag clearing logic, but no concurrency/race case is actually committed there. The *closest* precedent is Story 1.2's review process itself independently verifying `setStock()` under 20-way concurrency by hand (documented in that story's Review Findings) — never turned into an automated test. This story's Task 5 concurrency test is therefore the **first** committed concurrency test in this codebase, not an extension of an existing one. Build it from the general Playwright `Promise.all` pattern already used elsewhere in this suite (e.g. `payment.spec.ts`'s `Promise.all` around `waitForResponse` + a click), not from a `tests/inventory.spec.ts` precedent that doesn't exist.

**The pre-existing webhook idempotency gap this story closes was already flagged, generally, before this story existed.** `project-context.md`'s Critical Don't-Miss Rules: *"Webhook is not idempotency-guarded beyond `smsNotified` — don't assume replay-safety when extending it."* This story is the first "extension" of that route since that note was written — AC #6 exists specifically because of it. Once this story ships, update that `project-context.md` line to reflect that stock-decrement is now also replay-guarded (via the `status`-transition check), same as `smsNotified` — don't leave the note describing a gap that no longer exists.

**Neon's pooled `DATABASE_URL` and interactive transactions:** this codebase's `DATABASE_URL` goes through Neon's connection pooler (PgBouncer-style, transaction-pooling mode per `project-context.md`), while `DIRECT_URL` is unpooled and reserved for migrations. Prisma's `$transaction(async (tx) => {...})` (interactive transactions) needs a stable connection for the duration of the callback. This has never been exercised in this codebase before (no `$transaction` calls exist yet). It's expected to work fine over Neon's pooler for a short, simple transaction like this one (no long-running work inside it, no session-level features used) — but if Task 6's tests show connection errors specific to transaction handling (not just flaky test infra), that's a real signal worth investigating rather than dismissing, not a known-safe assumption to wave away.

- Migration hygiene doesn't apply this story (no migration) — but if the dev agent's implementation ends up needing one after all (e.g. a design deviation from this story's recommendation), the standing rule is `npx prisma migrate dev`, never `prisma db push`.
