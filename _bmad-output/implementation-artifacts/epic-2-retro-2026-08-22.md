## What Went Well

- **One-round closure across the board.** Unlike Epic 1 (Story 1.2 alone took 4 rounds), all three Epic 2 stories stabilized on the first review pass. The stories were smaller and more tightly scoped (each had one clear new capability layered on the previous story's infrastructure), which likely explains a lot of this.
- **Cross-epic pattern reuse worked.** Story 2.3's deactivate-route race was fixed with the exact atomic-claim pattern (`updateMany({ where: { ...guard } })` + re-read) that Epic 1's Story 1.4 built and hardened over 3 review rounds for the Stripe webhook's `stockDecremented` flag. The pattern transferred cleanly to a new context without needing to be rediscovered.
- **A prior review's own process mistake was caught and not repeated two stories later.** Story 2.2 pushed its ATDD red-phase scaffolds to `main` as a standalone commit and broke CI's typecheck gate. Story 2.3 explicitly cited that mistake in its own Dev Notes and deliberately implemented straight through to green before its first push — confirmed via `gh run watch` that CI stayed green the whole way.
- **Forward-flagged decisions actually got picked up.** Story 2.2's review logged a deferred question ("should a deactivated vendor's slug become reusable?") for Story 2.3's planning to resolve. It did — the user was asked directly during 2.3's planning and made an explicit, reasoned call (leave slugs permanently reserved). Same pattern with `getCurrentAdmin()`'s fail-open-by-convention design: flagged in 2.1's review, explicitly reconfirmed (not silently dropped) during 2.2's planning.
- **Honest reporting of untested surface stayed a habit, not a one-off.** Every story's Dev Agent Record explicitly named what wasn't verified (e.g. 2.3's admin vendor-list UI has no dedicated e2e coverage and wasn't manually browser-verified) rather than overclaiming "verified working."

## What Slowed Us Down / Recurring Problems

**1. The Epic 1 retro's #1 action item — provision real Admin e2e credentials — was never actually completed, and the cost compounded every story.** Story 2.1 built the entire admin auth-fixture *infrastructure* (seed row, extended `global-setup.ts`, `.env.example`, CI wiring) but the actual `E2E_ADMIN_EMAIL`/`E2E_ADMIN_CLERK_ID` secrets were never provisioned (an external, human-owned step, not something a dev-story pass can do). Result: expected e2e skips grew story over story — 1 (Story 2.1) → 6 then 8 (Story 2.2) → 11 (Story 2.3). By the end of the epic, **zero** of the admin-authenticated e2e tests across all three stories had ever run for real; every one of them is provably correct only by manual code cross-check, not execution. This is the single largest carried-forward risk into Epic 3, which is admin-only in the same way.

**2. The ATDD scaffold-activation script's blanket `test.skip(` → `test(` bug hit twice.** Story 2.2 hit it (two `beforeEach` conditional-skip calls briefly mis-converted), caught and fixed in-story. Story 2.3 hit the *identical* bug again and said so explicitly in its own Debug Log ("this activation script is now 2-for-2 on this exact mistake"). Nothing changed about the activation method between the two occurrences — the lesson was named but not converted into a process fix.

**3. Documentation drift was found in every single review round, again.** This is Epic 1's insight #3 repeating verbatim in Epic 2: 2.1's review found 3 stale docs (middleware matcher scope), 2.2's found a self-contradicting source-tree comment and a doc line describing a self-registration flow that doesn't exist, 2.3's found an inaccurate "before anything else runs" claim and a deactivate-route section describing the pre-fix check-then-act shape after the route itself had already changed. Same root cause as before: doc updates are consistently a *review finding*, never something the implementation pass catches on its own.

**4. The same class of concurrency bug (check-then-act race) shipped in two consecutive stories.** 2.2's slug-uniqueness check and 2.3's deactivate-idempotency check were both non-atomic read-then-write sequences that a reviewer had to catch and convert to an atomic DB-level claim. Epic 1's insight #1 already named this exact failure mode as where multi-round review earns its keep — Epic 2 shipped it twice in three stories, meaning the lesson ("check-then-act is not a safe default for anything touching shared mutable state") still isn't reliably applied *during* implementation, only caught in review.

## Key Insights

1. **A completed retro action item and a *closed* one aren't the same thing.** Epic 1's retro marked the auth-fixture item "in-progress" with a clear note that the admin half was blocked on Epic 2's identity existing first. That was accurate at the time, but nothing re-surfaced it as still-open once Epic 2 actually started — it just quietly grew story over story instead of getting escalated. A carried-forward action item needs an owner and a trigger to re-check it, not just a note explaining why it's not done yet.
2. **Doc-drift and check-then-act races are now two-epic-old patterns, not first-time surprises.** Both were explicitly named in Epic 1's retro and both recurred at roughly the same rate in Epic 2. Naming a pattern once in a retrospective doesn't appear to change developer behavior during implementation — only a review pass reliably catches either one. Worth trying something structural (a pre-review self-checklist, or grep-able markers) rather than relying on the retro alone to carry the lesson forward a third time.
3. **Small, tightly-scoped stories with a real prior-story foundation to stand on close faster.** All three Epic 2 stories built directly and explicitly on the immediately preceding story's infrastructure (2.2 on 2.1's gate, 2.3 on 2.2's `createdByAdminId` relation-naming foresight) and all closed in one round. This is the same shape as Epic 1's Story 1.6 (small because 1.2 had over-built the primitive it needed) — worth treating as a repeatable planning heuristic, not a coincidence.

## Next Epic Preview — Epic 3: Admin Inventory Oversight

2 stories: 3.1 (admin inventory dashboard, read-only, reuses Story 2.1's `getCurrentAdmin()` gate directly) and 3.2 (low-stock SMS alert to admin, adds `Admin.phone` and hooks into Story 1.4's `decrementStock()`).

### Dependencies on Epic 2 work
Direct and already proven: 3.1's own AC states it "reuses Story 2.1's `getCurrentAdmin()` gate" — that gate has now shipped, been reviewed, and served three stories without a reported defect in the gate itself. No new admin-identity work needed.

### Dependencies on Epic 1 work
`stockQuantity`, `lowStockThreshold`, and `decrementStock()` all already exist and are the most heavily concurrency-hardened code in the codebase (3 review rounds in Story 1.4). Story 3.2 explicitly mirrors the existing `smsNotified` one-shot-flag pattern for its own `lowStockAlerted` flag — a pattern already proven safe, not a new design.

### Critical path before Epic 3 starts

1. **Resolve the E2E admin credential gap for real, not just document it a third time.** Epic 3 is 100% admin-authenticated, same as Epic 2. If the credentials are provisioned before Epic 3 starts, three epics' worth of admin e2e tests (2.1–2.3 plus whatever 3.1/3.2 add) all start running for real at once. If not, Epic 3 will report the identical "N expected skips" pattern a third time, and the real coverage gap keeps growing.
2. **Decide, once, whether `getCurrentAdmin()` needs a fail-closed `requireAdmin()` variant before Story 3.2 ships an SMS-triggering path.** This has been deferred twice (2.1's review, reconfirmed in 2.2's planning) with the reasoning "no route has forgotten the check yet." Story 3.2 is the first admin route whose failure mode (a wrongly-triggered SMS) has a real-world, non-database consequence. Worth a final explicit decision before, not during, that story.
3. **No epic-plan-changing discoveries from Epic 2 affect Epic 3.** The architecture, schema shape, and admin-gating pattern Epic 3 depends on all landed exactly as planned — no rework needed to Epic 3's own definition.
