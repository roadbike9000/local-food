# Spine Pair Review — local-food

## Overall verdict

The spine pair is genuinely close to source-extractable: every `{path.to.token}` reference in both files resolves cleanly against `DESIGN.md`'s frontmatter, component/token naming is identical everywhere it's used, section shape and order are canonical, and the State Patterns table is unusually disciplined (grounded in real code paths, distinguishing mocked vs. spine-only per row). The gaps that remain are narrow but real: the persistent site header / cart pill — present on every single screen — has a behavioral spec in `EXPERIENCE.md` but no visual spec in `DESIGN.md`; six frontmatter tokens (five typography, one component) are defined but never tied to a documented usage anywhere in prose, even though the mockups show exactly where they belong; the `sources` frontmatter points at a PRD about an unrelated admin/inventory feature rather than at `.memlog.md`, which actually carries this redesign's decision trail (including three rejected whole directions that don't survive into either finished spine); and the single Key Flow never walks the two in-scope cart-editing behaviors (remove line, adjust quantity) that its own Component Patterns table calls out as real rules. None of this blocks a downstream consumer, but each is a place where they'd have to re-derive a decision from the mockups or the memlog rather than read it off the spine.

## 1. Flow coverage — thin
Checked: `EXPERIENCE.md` has one Key Flow ("Saturday brunch order — Renata"), evaluated against the PRD's three Key User Journeys (UJ-1 admin removes vendor, UJ-2 customer edits cart, UJ-3 admin low-stock alert) and against this spine's own Component Patterns / State Patterns tables, since UJ-1/UJ-3 are admin-scope and explicitly out of bounds for a storefront-only pass.
### Findings
- **medium** The only Key Flow never exercises the two customer-facing cart-editing behaviors this spine itself specifies as real rules — the quantity stepper (Cart item row, `EXPERIENCE.md` line 55-56) and the remove-line-item link (same row). Renata only ever adds items; nothing dramatizes UJ-2 ("customer edits a cart," the one customer UJ in the PRD) even loosely. (`EXPERIENCE.md` Key Flows, lines 104-116). *Fix:* extend Flow 1 with a step where Renata decrements a quantity or removes a line before checkout, or add a short second flow for the edit path.
- **low** No flow (or flow branch) walks the deactivated-vendor state or the sold-out-item-already-in-cart state, even though both are richly specified in State Patterns — a downstream reader sees the rule but never sees it dramatized end-to-end the way the happy path is. (`EXPERIENCE.md` State Patterns, lines 76 and 79). *Fix:* optional — a short second flow or an added failure branch would close this; low priority given hobby-project stakes and that the state rows themselves are already concrete.
- Positive: the one flow present is well-formed per spec — named protagonist, numbered steps, an explicit climax beat, and a failure branch appended at the end.

## 2. Token completeness — adequate
Checked: every color in the YAML frontmatter has a hex value (no missing pairs); extracted all `{path.to.token}` references from both files' prose (grep) and verified each resolves against the frontmatter keys; checked which load-bearing color combinations have a stated contrast ratio.
### Findings
- **medium** Contrast ratios are stated for only five pairings (sage-light/olive-deep 7.49:1, sold-out-bg/ink-soft 5.92:1, ink/paper 15.6:1, ink-soft/paper 8.0:1, ink-soft/cream 7.0:1). The most-used interactive pairing in the entire system — `{colors.paper}` text on `{colors.terracotta}` fill (every pill button) — has no stated ratio, nor does `{colors.terracotta-deep}` heading text on cream/paper. Only a blanket "every pairing below was re-checked and passes ≥4.5:1 for body text" claim covers the rest, which doesn't obviously include button labels or display headings. (`DESIGN.md` Colors, lines 258-269). *Fix:* state the ratio explicitly for button-label-on-terracotta and heading-on-paper/cream, the two highest-traffic combinations left unstated.
- No critical misses: zero `{path.to.token}` references in either file fail to resolve against `DESIGN.md`'s frontmatter — a clean mechanical result.

## 3. Component coverage — adequate
Checked: extracted every component name used anywhere across both spines (table rows, bold headers, `{components.*}` references) and cross-referenced DESIGN.md.Components against EXPERIENCE.md.Component Patterns for a matching row with real rules on both sides. Cross-checked against the mockups' actual CSS to confirm which frontmatter tokens map to which rendered elements.
### Findings
- **high** "Cart pill (header)" has a real behavioral row in `EXPERIENCE.md.Component Patterns` (line 59: "Shows a live item count badge... plain link to `/cart`") but **no corresponding row in `DESIGN.md.Components`** — its anatomy, size, and count-badge treatment are undocumented despite it appearing on every single screen in every one of the four approved mocks. The only DESIGN.md mentions are incidental (it gets `{rounded.full}`, and icons inherit color inside it). *Fix:* add a Components row for the header cart pill — background, badge styling/position, count-numeral typography.
- **medium** Five typography tokens (`headline-md`, `card-title`, `item-title`, `item-title-lg`, `price`) and one component token (`circular-thumb`) are defined in `DESIGN.md` frontmatter but never referenced — not even by plain-text name — anywhere in either file's prose. Cross-checking the mockups' CSS confirms real intended usage (`headline-md`→"Menu" section heading, 28px in `direction-artisanal-warm-v3.html`; `card-title`→homepage vendor-card name, 24px in `screen-homepage.html`; `item-title-lg`→product name, 21px), but that mapping exists only in the HTML, not in either spec document — a downstream consumer reading the prose alone cannot learn which token to apply to a vendor-card title, a product-row name, or a price display. (`DESIGN.md` frontmatter lines 50, 60, 65, 70, 115, 215; Components section, lines 312-324). *Fix:* add one line each to the Components section tying these tokens to the rows they belong to (e.g., "Vendor card title uses `{typography.card-title}`").
- **medium** `card-title` and `headline-sm` are byte-for-byte identical (Georgia, 24px, weight 400, lineHeight 1.2) with no documented distinction between them — both appear at 24px in `screen-homepage.html` (the section heading and the vendor-card name use the same rendered size). *Fix:* either collapse to one token or state explicitly what role-based distinction justifies keeping both.
- **low** Input fields have a visual spec in `DESIGN.md.Components` but no matching row in `EXPERIENCE.md.Component Patterns` — no behavioral rule for required state, phone-number formatting, or inline validation display for the cart's name/phone fields. *Fix:* low priority given the fields are simple text inputs, but a one-line behavioral row would close the pattern gap.
- The rest of the roster (buttons, badges, cards/rows, vendor card, pickup banner, squiggle divider, icons, quantity stepper, pickup-option, confirmation card) all have real, matching specs on both sides — not one-word descriptions.

### Findings

- **low** No cold-load/loading-skeleton state for the Homepage, though this is plausibly a non-issue given Server Component rendering with no client fetch in the loop.

## 7. Inheritance discipline — thin
Checked: whether `sources` frontmatter resolves and actually backs the content; whether UJ/FR names are traceable; whether component/token names are identical everywhere they're used.
### Findings
- **high** The `sources` frontmatter in both files points solely to `prd-local-food-2026-08-10/prd.md` — the "Admin & Inventory Expansion" PRD, whose nine FRs are entirely about a platform-admin role, vendor onboarding/offboarding, and stock-quantity tracking. It resolves mechanically (the file exists) and does supply real, correct grounding for a handful of this spine's decisions — the out-of-stock states trace to FR-6/FR-7, the cart stepper to FR-11, the deactivated-vendor message to FR-4's exact copy. But a downstream consumer opening the cited source looking for the rationale behind *this redesign* — why redo the storefront's look at all, why Terracotta & Olive, why reject the other three rendered directions — will find nothing; that entire decision trail lives in `.memlog.md`, which is never cited in either file's `sources` frontmatter. (`DESIGN.md` line 5 has no `sources` field at all — only `EXPERIENCE.md` does, line 5.) *Fix:* add `.memlog.md` as a second `sources` entry in `EXPERIENCE.md` (and consider adding a `sources` field to `DESIGN.md`, which currently has none), since it's the document that actually carries the design-direction reasoning.
- **low** No FR or UJ ID is cited anywhere in either file's prose, even where a decision clearly traces to one (e.g., the cart stepper → FR-11, the deactivated-vendor copy → FR-4). The connection is real but implicit — a downstream reader has to re-derive it rather than follow a citation. *Fix:* low priority for a hobby project; a parenthetical FR reference at the relevant State/Component Pattern rows would close it cheaply.
- Positive: token and component names are used identically and correctly across both files everywhere they're referenced via `{path}` syntax — a full grep-based cross-check found zero naming drift.

## 8. Shape fit — adequate
Checked: DESIGN.md section order against the canonical list; EXPERIENCE.md required-default sections; required-when-applicable sections against what `.memlog.md` and the sources actually show.
### Findings
- **medium** `.memlog.md` explicitly documents three whole rejected directions (premium-minimal, modern-editorial, bold-playful — the last one taken through a full repaint variant before being dropped) plus a fixed contrast bug and an explicit no-emoji/no-confetti decision. Per this spec, that's exactly the trigger for a required-when-applicable **Inspiration & Anti-patterns** section, and neither file has one. `DESIGN.md`'s Do's and Don'ts captures component-level anti-patterns (no emoji, no dead buttons) but not the higher-level "why this direction over the other three" record — a downstream architect or story-author has no way to learn that bold-playful was seriously explored and dropped, or why, without reading the memlog directly. (Compare the shadcn example's own `Inspiration & Anti-patterns` section, which exists for exactly this purpose.) *Fix:* add a short Inspiration & Anti-patterns section to `EXPERIENCE.md` (or a closing subsection of `DESIGN.md`'s Brand & Style) naming the three rejected directions and the one-line reason each was dropped.
- DESIGN.md section order is canonical and complete: Brand & Style → Colors → Typography → Layout & Spacing → Elevation & Depth → Shapes → Components → Do's and Don'ts.
- EXPERIENCE.md carries all eight required defaults (Foundation, IA, Voice and Tone, Component Patterns, State Patterns, Interaction Primitives, Accessibility Floor, Key Flows), in canonical order.
- Responsive & Platform is correctly omitted per the project's explicit desktop-primary, single-form-factor scoping — not penalized, per this review's instructions.
