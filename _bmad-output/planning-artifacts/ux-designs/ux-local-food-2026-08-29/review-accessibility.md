# Accessibility Review — local-food storefront redesign

## Overall verdict

DESIGN.md's body-text contrast work is genuine and verifiable — I recomputed all six "Verified pairings" ratios independently and every one matches the documented number. The spine also correctly preserves several real accessibility patterns from the live app: the whole-card `<a>` link, badge-as-status-text (not a tab-stop), the `<fieldset>`/`<legend>`/real-radio requirement for 2+ pickup slots, and `ProductCard.tsx`'s `aria-disabled` + `aria-describedby` pattern. But the audit that produced the "passes ≥4.5:1" claim only covered six text-on-background pairs — it never checked non-text UI-component-boundary contrast (WCAG 1.4.11), and two of those un-checked tokens (input-field border, disabled-radio border) fail 3:1 badly enough to make form-field and disabled-slot boundaries nearly invisible. Focus-visible styling is specified for exactly one component (the vendor card) and silent on every button, input, and radio in the system. Three places in the spine assert "matches the existing pattern" in ways that don't hold up against the actual source (`Navbar.tsx` cart-pill labeling, the stepper's `aria-describedby` claim, and the premise that `role="alert"` is already used in the cart page) — these are documentation-accuracy risks that could cause an implementer to skip work that still needs doing.

## Findings

- **high** Input-field border and fill are both far below the WCAG 1.4.11 non-text 3:1 minimum for a UI-component boundary. `{colors.line}` (`#ddc79f`) on `{colors.cream}` fill measures 1.41:1, and on `{colors.paper}` (the checkout panel background) measures 1.62:1; the `cream`-vs-`paper` fill itself is only 1.15:1 apart. On the busiest screen in the app (`screen-cart.html` `.field input`, `DESIGN.md` `components.input-field`), the name/mobile-number fields have no reliably perceivable boundary except the field-label text sitting above them. *Fix:* give `input-field` a border color that hits ≥3:1 against both `cream` and `paper` (the current palette's `disabled-outline` #b9ab8c only reaches 2.2:1 against paper and isn't sufficient either — a new, darker dedicated tone is needed), or deepen the fill color so the field itself reads as a distinct region.

- **high** No visible focus indicator is specified for any interactive element except the vendor card. `EXPERIENCE.md` Accessibility Floor (line 94) defines "a visible focus ring in `{colors.terracotta}` against `{colors.paper}`" only for the whole-card `<a href="/vendors/{slug}">`. Every other focusable control in the system — Add-to-cart, Checkout, Back-to-vendors, the quantity stepper's `−`/`+` buttons, the "remove" link, the name/phone `<input>`s, each pickup-time radio `<input>`, and the header cart-pill link — has zero documented focus treatment anywhere in `DESIGN.md` or `EXPERIENCE.md`. *Fix:* promote the terracotta focus ring to a named token (e.g. `components.focus-ring`) and apply it system-wide; the color itself is fine (terracotta measures 6.07:1 on paper and 5.28:1 on cream, both comfortably clearing the 3:1 non-text minimum), it just needs to not be scoped to one component.

- **medium** Placeholder-text contrast fails the AA body-text bar despite DESIGN.md's blanket "every pairing below was re-checked and passes ≥4.5:1" claim. `{colors.placeholder-text}` (`#9c8a70`) measures 2.86:1 against `{colors.cream}` (the actual input fill it renders on) and 3.28:1 against paper — both below 4.5:1, and below even the 3:1 large-text floor. The "Verified pairings" comment block in `direction-artisanal-warm-v3.html` (lines 32–38) lists six text pairings but never includes this token, so the blanket claim doesn't actually cover it. (Location: `DESIGN.md` Colors section / `components.input-field.placeholderColor`; `screen-cart.html` `.field input::placeholder`.) *Fix:* darken `placeholder-text`, or explicitly document it as an accepted exception with its real ratio — don't let it ride on the "every pairing" claim.

- **medium** The disabled/full pickup-slot radio-dot border fails 3:1 non-text contrast. `{colors.disabled-outline}` (`#b9ab8c`) measures 2.23:1 against paper and only 1.65:1 against its own row background (`{colors.sold-out-bg}`) — the radio-dot's visual boundary is barely perceivable in the "Full" state (`screen-cart.html` `.radio-dot.disabled`, `.pickup-option.full`). This doesn't leave users without the information — the "Full" `badge-negative` text (5.92:1) reliably communicates unavailability on its own — but the control itself is effectively invisible as a shape. *Fix:* either darken `disabled-outline` to clear 3:1, or drop the visible radio ring entirely for disabled rows and let the row background + badge carry the state (simpler and already sufficient).

- **medium** Hero-photo caption text has no contrast guarantee against the live photo underneath it. The caption ("Fresh from this morning's bake," `direction-artisanal-warm-v3.html` `.hero-photo .caption`) relies solely on a `linear-gradient(180deg, rgba(43,32,21,0) 45%, rgba(43,32,21,0.55) 100%)` overlay plus a `text-shadow: 0 1px 3px rgba(0,0,0,0.4)` — both are mitigations, neither is a floor. A bright, high-key crop (light crust, flour dusting, a cream tablecloth corner) at that exact bottom-left position could still drop well below 4.5:1, and nothing in `DESIGN.md` sets a minimum-guarantee mechanism despite this being a flagged variable-contrast risk. *Fix:* add a solid or near-opaque caption plate (e.g., a small `terracotta-deep` chip behind the text) so contrast is deterministic regardless of the underlying photo, rather than depending on gradient + shadow alone.

- **medium** The header cart-pill accessible-name claim doesn't match the actual current implementation, and the new icon has no `aria-hidden`. `EXPERIENCE.md` Accessibility Floor (line 95) says the cart pill should read "Cart, 2 items… matching the existing pattern of a visible numeral plus an accessible name, not the numeral alone" — but `src/components/Navbar.tsx` (lines 19–26) has no `aria-label` on the cart `<Link>` at all today; it's bare "Cart" text plus an unlabeled `<span>{count}</span>`. The redesign mocks also add a decorative basket SVG (`screen-homepage.html`, `screen-cart.html`, `screen-checkout-success.html`, the `.cart` element) with no `aria-hidden="true"`. Because the spine frames this as "matching the existing pattern," an implementer could reasonably conclude no labeling work is needed and ship the new icon+badge combo exactly as unlabeled as it is now. *Fix:* correct the spine's premise, and explicitly require `aria-label={\`Cart, ${count} items\`}` on the link plus `aria-hidden="true"` on the basket SVG.

- **medium** Dynamic error/warning text in the in-scope customer components has no live-region behavior today, and the redesign doesn't add any. `src/app/cart/page.tsx` renders the checkout error (line 283), the pickup-slots-fetch-failed message (line 229), and the "No longer available — remove to continue" warning (lines 191–195) as plain `<p>` text with no `aria-live` or `role="alert"` — that pattern exists elsewhere in the codebase (`EditStockControl.tsx`, `AddProductForm.tsx`, etc., all admin/dashboard, out of scope) but not in the customer-facing cart page or `ProductCard.tsx`. `EXPERIENCE.md`'s State Patterns table documents the visual treatment for all three states (keep red-600 text) but says nothing about adding an announcement mechanism. These messages gate checkout completion, so a screen-reader user gets no notification when one appears unless they happen to re-scan the page. *Fix:* add `role="alert"` + `aria-live="polite"` to these three messages as part of the redesign pass, matching the pattern already used elsewhere in the app.

- **medium** Quantity-stepper markup risk: the mock renders fake, non-interactive controls, and — unlike the pickup-option component — nothing in the spine explicitly guards against building it that way. `screen-cart.html` `.qty-stepper` is three plain `<div>`s (`cursor: default`), not the real `<button aria-label="Decrease/Increase quantity of X">` + `<span aria-live="polite">` pattern `cart/page.tsx` (lines 154–178) already ships. `EXPERIENCE.md` line 98 explicitly says the pickup-option's "visual radio-dot styling… wraps a real input, it doesn't replace one" — there's no equivalent sentence for the stepper, even though it's the same static-mock risk. *Fix:* add a matching one-line guardrail for the quantity stepper, e.g. "the `qty-btn` pill styling wraps real `<button>` elements with their existing `aria-label`s — it doesn't replace them."

- **low** The Accessibility Floor's claim that disabled stepper buttons use `aria-disabled` + `aria-describedby` "exactly as… the cart page already implement[s]" is inaccurate for the stepper specifically. `ProductCard.tsx`'s Add-to-cart button does use that pattern (lines 107–108, pointing at `outOfStockId`). The cart page's stepper buttons (lines 154–178) use native `disabled` — not `aria-disabled` — and have no `aria-describedby` or associated limit text to point at. This is a documentation-accuracy issue, not a shipped bug (native `disabled` is itself fully accessible), but it could send an implementer looking for a "limit text" element for the stepper that doesn't exist anywhere in the design. *Fix:* split the sentence so it describes each component's real, different pattern instead of conflating both under one "exactly as" claim.

- **low** Whole-card vendor link reads more verbosely with the new "View menu" pill, though this is not a regression. The mock wraps kicker + name + description + availability badge + "View menu" text all inside one `<a>` (`screen-homepage.html` `.vendor-card`), matching `VendorCard.tsx`'s existing pattern of wrapping name + description + item-count in one link today. The only new addition is the "View menu" label text, which adds one extra phrase to the end of every card's link announcement. Not a WCAG failure (it's informative content, not decorative noise), and no fix is required — just worth knowing the announcement gets a bit longer.
